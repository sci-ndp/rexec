How Rexec Works

What happens when you call a remote function: what gets sent, where it runs, what carries over between calls, and what you'll see when something fails.

Overview

Rexec turns a decorated Python function into a remote call. You get one dedicated server on the cluster. Each time you call the function, its code and arguments are serialized on your machine, routed through the broker to your server, and run there in a new process.

Your notebook

@remote_func serializes the function and its arguments with dill.

Broker

Checks your token on every message and routes the call to your server by user ID.

Your server pod

One per user. Runs calls one at a time, in the order they arrive.

Fresh process

Runs the function, streams stdout and stderr, then sends the return value or the error.

Output travels back the same way: printed output while the function runs, then the result.

Summary of Execution Semantics

The following nine properties characterize how Rexec executes user code. Each property is examined in detail in the section indicated.

  1. Each user is assigned a single server, shared across all sessions. All notebooks and scripts authenticated under the same user identity dispatch their calls to the same server instance. See Your Environment.
  2. The Python version of the server must match that of the client. Functions are transmitted as Python bytecode, the format of which varies between interpreter versions. The version should therefore be pinned in the requirements specification (e.g., python==3.11). See Your Environment.
  3. A call transmits only the function and its arguments. Module-level imports, global variables, and helper functions defined in the calling notebook are not transmitted. They must be defined within the function body or supplied as arguments. See Remote Calls.
  4. Only positional arguments are supported. A call of the form f(16) succeeds, whereas f(x=16) raises TypeError. See Remote Calls.
  5. Standard output is streamed during execution. The return value is delivered upon completion. Exceptions raised on the server are reported to the client as RuntimeError. See Remote Calls.
  6. Calls are executed sequentially, in order of arrival. A subsequent call does not begin until the preceding call has completed. See State Between Calls.
  7. Each call is executed in a new process. In-memory state does not persist between calls. Files written to the server's local disk persist until the server is restarted, replaced, or terminated. See State Between Calls.
  8. Calls are neither retried nor subject to a timeout. If the server or the broker fails during execution, the call blocks until the user interrupts it. See When Things Fail.
  9. A server remains active until it is explicitly terminated. No idle-shutdown mechanism is provided yet. Users should call terminate_rexec_environment() upon completion of their work. See Lifecycle.

Remote Calls

Decorating a function with @remote_func replaces it with a remote call. Calling it serializes the function and its arguments with dill, sends them to the broker with your token, and waits for your server to answer.

What travels with a call

Sent to the server

  • The function's code, if it is defined in the notebook or script you run
  • Positional arguments
  • Default argument values and closure variables, captured when the function is defined
  • Your token, which the broker checks on every message

Not sent

  • Imports at the top of your notebook
  • Global variables and helper functions defined elsewhere in the notebook
  • Functions from your own local modules (the server can't import them)
  • Local files and environment variables

On the server, anything the function neither defines nor receives fails with NameError, or ModuleNotFoundError for a local module.

import math                        # top-level import: not sent
SCALE = 3                          # global variable: not sent

@remote_func
def bad(x):
    return math.sqrt(x) * SCALE    # NameError on the server

@remote_func
def good(x, scale=SCALE):          # SCALE's value is captured here
    import math                    # import inside the function
    return math.sqrt(x) * scale

good(16)      # returns 12.0
good(x=16)    # TypeError: keyword arguments aren't supported

What comes back

On the serverWhat you see locally
print() / stdoutPrinted in your notebook while the function runs.
stderrWritten to your local stderr while the function runs.
return valueReturned by the call when the function finishes. A function that returns nothing gives None.
raiseRuntimeError("An unexpected error occurred: <message>"), raised after any streamed output. The original exception type and traceback stay in the server's logs.
yieldNot supported. Yielded values are dropped and the call returns None.
ⓘ
Both sides need the libraries. Arguments and return values must be picklable, and their packages must be installed on both sides. Returning a pandas DataFrame, for example, needs pandas on your machine too.

Interrupting a call

Stopping the cell (Ctrl-C, or the stop button in Jupyter) cancels the call. The server terminates the process running it (SIGTERM, then SIGKILL after half a second) and KeyboardInterrupt is raised locally.

Your Environment

setup_rexec_environment() asks the Deploy API for a server built from your requirements. The server is identified by your user ID (the sub claim in your token), so you have exactly one, and every session signed in as you uses it.

What's installed

  • The official python:<version> container image, for the version you pin.
  • scidx-rexec and its dependencies (dill, pyzmq, dxspaces, packaging, cryptography).
  • Your requirements, installed with pip install -r.

Requirements file rules

  • Pin Python exactly with one python==X.Y line, matching your local Python's major and minor version.
  • Use standard pip requirement lines. Direct URL references (pkg @ https://…) are rejected.
  • Full-line # comments are fine. Comments at the end of a line are not, and make setup_rexec_environment() raise InvalidRequirement.
  • Line order doesn't matter: the same set of lines is the same environment.
# requirements.txt
python==3.11
numpy==2.1.3
pandas>=2.2
A Python version mismatch breaks calls. A function sent from Python 3.13 to a 3.11 server doesn't run. Depending on the versions, the call prints Invalid function payload: … and returns None, or it crashes the server process and the call hangs.

What setup_rexec_environment() does

Your serverYou ask forResult
None yetAny requirementsCreated. A new pod starts in namespace rexec-server-<user-id>.
RunningThe same requirementsNo change. The running server and its files are untouched.
RunningDifferent requirementsConflict (HTTP 409). Nothing changes.
RunningDifferent requirements with force=TrueReplaced. A new pod replaces the old one. A call the old pod was running is interrupted.
AnyInvalid requirementsError (HTTP 500) with the reason, for example a missing python== line.
Conflicts and server-side errors don't raise. setup_rexec_environment() returns the Deploy API's response whatever happened. Its Status tells you which of the outcomes above you got. A login or permission problem comes back as detail instead. 
resp = ndp_ep_client.setup_rexec_environment(requirements="requirements.txt")
print(resp)    # {"Status": "...", ...} or {"detail": "..."}
force is in scidx-rexec (remote_func.set_environment(path, token, force=True)), but ndp_ep's setup_rexec_environment() on GitHub main doesn't accept it yet; it's on branch feat/rexec-force-terminate. Update the table above once that's released.

Starting takes a while

setup_rexec_environment() returns as soon as Kubernetes accepts the new server, before the pod has pulled its image and installed your packages. Until the server connects to the broker, calls print Server not ready/available for user <id>. and return None. To wait for it: 

import time

@remote_func
def ping():
    return "ready"

while ping() != "ready":     # prints "Server not ready…" until the pod is up
    time.sleep(10)

State Between Calls

On your serverCarries over to the next call?
Variables, imported modules, objects in memoryNo. Each call runs in a new process.
Files your function writesYes, until the server restarts, is replaced or is terminated. They share the pod's 2 GiB disk limit with your installed packages.
Installed packagesYes, until you replace the server with different requirements.

Order

Your server runs one call at a time, in the order they arrive. A call from another cell, notebook or script waits until the current one finishes.

Interrupting affects the shared server. Interrupting a call stops whichever call is running on your server at that moment, even if another of your sessions started it.

Lifecycle

Rexec doesn't report these states yet (there is no status API). They describe what is happening at each stage.

Your server

StateWhat it meansWhat comes next
startingThe pod pulls the Python image, installs packages and starts the Rexec server. Calls print "Server not ready".ready, once it connects to the broker
readyConnected to the broker and idle.busy, when a call arrives
busyRunning a call. Other calls wait in line.ready, when the queue is empty
restartingThe container crashed or was evicted and Kubernetes restarts it. Files are lost; packages reinstall.starting
replacedYou called setup_rexec_environment() with new requirements and force=True.starting, as a new pod
terminatedYou called terminate_rexec_environment(). Your namespace and everything in it are deleted.None. Call setup_rexec_environment() to start again.

There is no idle shutdown and no time limit. A server keeps running, and keeps its resource reservation, until you terminate it. Terminating also kills any call it is running. 

ndp_ep_client.terminate_rexec_environment()
plan.md marks "Server Lifecycle & Shutdown" as done, but none of the Rexec repos on GitHub has idle-shutdown or max-duration code. Confirm this paragraph before publishing.

A single call

StateWhat it means
queuedYour server is still busy with an earlier call.
runningExecuting in a fresh process. Output streams back.
completedThe function returned. The call returns its value, or None.

cancelledYou interrupted it. The process is terminated and KeyboardInterrupt is raised locally.

When Things Fail

What happensWhat you seeWhat to do
Your function raisesRuntimeError: An unexpected error occurred: …Fix the function. The server keeps running.
Your function's process dies, for example killed for using too much memoryRuntimeError: Execution process exited unexpectedly with code N.Reduce memory use. The server keeps running.
The server pod crashes or restarts during a callNothing. The call waits with no result and no error.Interrupt the cell. Call again once the server is back (packages reinstall; files are lost).
The broker restarts during a callNothing. The call waits.Interrupt the cell and call again.
No server is running, or it is still startingPrints Server not ready/available for user <id>. and returns None.Run setup_rexec_environment(), or wait for the server.
Your token is invalid or expiredPrints Token validation failed. and returns None. A call that is already running still returns its result.Get a fresh token.
The server's Python version doesn't match yoursPrints Invalid function payload: …, or the server crashes and the call waits.Pin your local version in the requirements and replace the server.
ⓘ
Rexec never retries. Each call runs at most once. If you call again after a hang, the first attempt may already have run; only its result was lost. Keep that in mind for functions that write files or send data elsewhere.

Isolation & Limits

Enforced today

  • Your server runs in its own Kubernetes namespace, rexec-server-<user-id>, and each call runs in its own process.
  • Every message to the broker, and every request to create or delete a server, is checked against the identity provider. Your sysadmin can also require membership in a group.
  • Your requirements reach the pod as a file for pip install -r, never through a shell command.
  • Each server pod has fixed resource limits:
ResourceReservedMaximumOver the maximum
CPU0.25 core2 coresSlowed down (throttled)
Memory512 MiB4 GiBThe function's process is killed (RuntimeError), or the whole server restarts, depending on the cluster
Disk512 MiB2 GiBThe pod is evicted and restarted; files are lost

These are the Deploy API's defaults; your sysadmin can change them. You can't request a different size.

Not guaranteed yet

  • Network isolation. Rexec doesn't create a network policy for server pods, so what they can reach, inside the cluster and on the internet, depends entirely on the cluster's own policies. By default, Kubernetes allows all of it.
  • Unprivileged execution. The server runs as root inside its container.
  • Encrypted transport. Traffic between your machine and the broker is plain TCP. Rexec doesn't encrypt your token, code or results on that link.

Not Yet Supported
